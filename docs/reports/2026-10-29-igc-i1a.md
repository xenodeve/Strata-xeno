# IGC I1a: typed exact integer execution on CUDA

Tracking: [#276](https://github.com/xenodeve/Strata-xeno/issues/276).
I1a's standalone CUDA component gates pass. I1b domains, learned adapters,
conversation integration and practical-use gates are still open.

## Implemented contract

`igc_exact.hpp` defines ABI 1: 160-byte requests and 88-byte results, at most
64 requests per launch. Operands are canonical signed decimal integers with up
to 62 digits. Operations are add, subtract and multiply. Requests carry domain,
operation, invocation and logical position; they contain no pointers or code.

The GPU validates version, reserved fields, invocation ID, digit range, canonical
zero/length/padding and supported domain/operation. Malformed, unsupported and
overflow results have an empty value, distinct from successful numeric zero.
Any result needing more than 62 digits returns overflow. Input width is not
silently truncated. The full-width integer times one and full-width plus zero
work within this ABI; incidental refusals of the secondary firmware are not
adopted as mathematical semantics.

All arithmetic runs in `src/kernels/igc_exact.cu`. The host API only validates
launch arguments and enqueues the kernel on an explicit created stream; it does
not parse expressions, compute answers, allocate per call or synchronize. Input
and output are internal caller-owned device arrays. The eventual controller must
fence before consuming results and bind ownership to accepted language inputs.
This component does not yet provide that model controller.

Each request uses bounded integer work. A multiplication cell accumulates at
most 62 products of decimal digits (62 × 81 before carry), safely within int32.
The temporary has 125 digits; the final capacity check precedes publication.
There are no float operations, atomics, mutable global state, firmware or model
weights in this exact executor. It is the software executor for the new IGC
primary path, distinct from the retained compiled-Qwenputer circuit.

## Verification

- Red-first stub: 6 tests failed as intended; the later sequence control also
  failed before its harness implementation.
- Final suite: **7 tests passed**, 1.254 seconds including process startup/I/O.
  It includes 256 frozen held-out signed cases, independent Python integer
  oracles, full-width carry/borrow/product boundaries, all three operations,
  malformed/unsupported/overflow controls and binary/batch limits.
- Native runs repeat and compare every result byte. A sequence mode reuses one
  device output slot across a large result, zero, overflow and `17 × 23 = 391`,
  checking that old digits or failed values do not survive.
- All four Compute Sanitizer tools pass on a fixed 64-record sequence:
  memcheck/initcheck/synccheck: **0 errors**; racecheck: **0 hazards**.
  The results from each tool are compared offline to the independent oracle,
  not merely accepted from the tool exit status. Each returns 45 successes,
  9 overflows, 8 malformed and 2 unsupported results, with identical bytes.
- The CLI accepts only request and result paths; it receives no expected values
  or oracle output. Python arithmetic is confined to the test oracle.

The 64-request input/output device buffers total **15,872 bytes**. This is a
buffer-size calculation, not a measured total memory peak: CUDA context/module,
thread-local compiler resources and eventual learned adapter/cache costs are
additional. No speed, quality, daily-use or latency comparison is claimed.

this prototype and untested; no cross-backend completion claim is made.

## Remaining work

I1b adds the separately specified division/rational/floor/modulo/gcd/power/decimal
domains and their exact failure contracts. I2/I3 must learn operands/readiness and
result injection from real Gyro activations, and I4 must validate repeated calls,
speculation, rollback, language caches and exactly-once consumption. These GPU
arithmetic results are not evidence that the model uses the executor yet.
The broader sandbox, programmable logic, geometry, upstream capability ledger and
end-to-end token/context/tool/latency goals remain in PRD R10.

Phase-comment publication is still blocked by the separately documented approval
integration problem; the local comment draft does not establish remote sync.
