# MIP + Sandbox: ทำไมกลไกทำงานแต่ผลยังไม่ขึ้น

วันที่ 2026-11-02 ข้อมูลจากแขนที่เก็บไว้บน A100 (LiveCodeBench hard 20 ข้อ) และบนเครื่องนี้ (MATH 300 ข้อ, GSM8K 200 ข้อ) ไม่ได้รันอะไรเพิ่มเพื่อรายงานนี้ นอกจากแขน `lg`

## สรุป

กลไกไม่ได้เสีย แต่ลงมือผิดจังหวะ และแก้ผิดจุด

- **Sandbox ทำงานก่อนมีอะไรให้ทดสอบ** แขนฐาน 66 % ของ token (448,404 จาก 684,271) อยู่หลังโมเดลเขียนร่างแรกเสร็จ แต่กฎเดิมเปิด block ที่ token 512 ซึ่งยังไม่มีร่าง จึงได้ค่ากลับมาแค่ 7 จาก 58 block
- **ค่าจาก MIP แก้ปัญหาที่แทบไม่มี** โมเดลใหญ่คิดเลขพลาดน้อยมาก ส่วนการคิดทดจริงคือการไล่ตัวอย่างและการสงสัยในตัวเอง ซึ่ง `A op B =` ไม่ครอบคลุม
- **กฎปิดความคิดตัดส่วนที่มีประโยชน์** ขณะที่ token ก้อนใหญ่อยู่ในการตรวจซ้ำที่โปรแกรมตอบแทนได้

แขน `lg` เป็นหลักฐานแรกว่าทางนี้ถูก ข้อ 3364 ที่เคยเสียกลับมาถูกที่ 12,782 token เพราะ test ผ่านแล้วจึงจบ

## ตัวเลข

### ค่าจาก MIP เอื้อมถึงแค่ไหน

| วัดบน | MATH 300 ข้อ | GSM8K 200 ข้อ |
|---|---|---|
| เครื่องหมาย `=` ในการคิด | 18,436 | 2,848 |
| นิพจน์ตัวเลขล้วนที่อ่านได้แน่นอน | 584 | 382 |
| ที่ regex ชี้ว่าผิด | 14 | 13 |
| อ่านแล้วผิดจริง (ข้อ) | 3 | 4 |
| อยู่ในข้อที่ตอบผิด | 1 จาก 27 | 2 จาก 25 |

อ่านครบทั้ง 27 บรรทัดที่ถูกชี้ ส่วนใหญ่ regex อ่านผิด เช่นช่วงเลข `60-69` หรือ `1/3 = 2 hours` ข้อที่ผิดจริงในแถวที่ตอบถูก โมเดลมักสงสัยเองในบรรทัดถัดมา

ตัวเลขนี้เป็นเพดานต่ำเกินจริงได้ เพราะเห็นแค่นิพจน์ตัวเลขล้วน และยังไม่ได้พิสูจน์ว่าบรรทัดที่ผิดเป็นสาเหตุของคำตอบผิด ข้อ 3608 ใน LiveCodeBench เป็นตัวอย่างของสิ่งที่ regex ไม่เห็น: `gcd` ของตัวเลขตัวเดียวผิดในหัว ทำให้เข้าใจโจทย์ผิดไปประมาณ 30,000 token

เมื่อแยกสิ่งที่อยู่ทางซ้ายของ `=` บน MATH: symbolic หรือข้อความ 69.7 %, ตัวเลขล้วน 10.0 %, การตั้งค่าตัวแปร 8.9 %, ตัวแปรที่รู้ค่าแล้ว 7.1 %, ฟังก์ชันของตัวเลขเช่น `gcd` และ `C(n,k)` 4.1 % เพิ่มตัวแปรและฟังก์ชันให้ MIP เอื้อมถึงได้อีกราว 11 %

### Sandbox ทำอะไรจริง

| แขน | เปิด block ที่ | block | ได้ค่ากลับมา | ไม่พิมพ์ | error | `None` | ไม่มีโมดูล |
|---|---|---|---:|---:|---:|---:|---:|
| `lsb` | 512 | 58 | 7 | 18 | 14 | 13 | 5 |
| `ls2` | 2,048 | 47 | 12 | 17 | 10 | 6 | 1 |
| `lnc` | 512 | 76 | 17 | 24 | 16 | 13 | 6 |

เฉลี่ย 20 % ของ block ให้ค่าที่ใช้ได้ และมี block แบบ brute force แค่ 3 จาก 181

### Token หมดไปตรงไหน

แขน `lon` ไม่มี MIP, 19 จาก 20 ข้อเขียนร่างเต็มในการคิด ร่างแรกอยู่ที่ token 1,654 ถึง 46,428

อ่านจุดกลางของ 4 ข้อที่ยาวที่สุดแล้วพบ 3 แบบ

| แบบ | ตัวอย่าง | ถ้ามีการทดลอง |
|---|---|---|
| สงสัยว่าวิธีถูกไหม แล้วไล่ด้วยมือ | 3781, `Let's test p right middle d=10` | brute force บน input เล็ก ตอบได้ในไม่กี่วินาที |
| ไม่แน่ใจว่าโจทย์หมายถึงอะไร | 3608 ราว 40,000 token ก่อนพบ `Good catch!` | เขียน brute force ตามโจทย์แล้วเทียบตัวอย่าง |
| ตรวจโค้ดที่เขียนเสร็จแล้วซ้ำ | 3674 มีโค้ดตั้งแต่ราว 8,500, คิดต่อถึง 33,000 ว่า `Now, let's think about if ...` | รันตัวอย่างและ input ขนาดใหญ่สุด |

API อ่านหน้าต่างละ 1,600 ตัวอักษร 301 จุดของแขนเดียวกัน ถ่วงน้ำหนักตาม token แล้วแยกตัวเลขตามข้อ 3460 ซึ่งวนนับ 261,415 token จนบังตัวเลขรวม

| งานที่ทำอยู่ | ทุกข้อ | ไม่รวม 3460 |
|---|---:|---:|
| พัฒนาวิธีคิด | 32.2 % | 47.1 % |
| ไล่ตัวอย่างด้วยมือ | 41.3 % | 20.3 % |
| ตรวจโค้ดที่เขียนแล้วซ้ำ | 15.5 % | 14.7 % |
| เขียนโค้ด | 6.9 % | 11.1 % |
| ทำความเข้าใจโจทย์ | 4.0 % | 6.5 % |

| โปรแกรมตอบแทนได้ไหม | ทุกข้อ | ไม่รวม 3460 |
|---|---:|---:|
| ไม่ได้ | 39.7 % | 59.2 % |
| ได้ ด้วยโปรแกรมเล็กตัวใหม่ เช่น brute force | 48.5 % | 39.8 % |
| ได้ ด้วยการรันร่างที่มีอยู่ | 11.8 % | 1.0 % |

ตัวเลขนี้คือความเห็นของ API ไม่ใช่สิ่งที่พิสูจน์แล้ว แต่ชี้ทางชัด: **ราว 40 % ของการคิดต้องใช้โปรแกรมตัวใหม่** การรันร่างอย่างเดียวจึงไม่พอ และงานแบบนี้กระจายอยู่ทุกช่วง ไม่ได้รออยู่หลังร่าง ช่วงแรกของการคิดก็มีถึง 44 %

### คำที่ใช้จับจังหวะไม่ได้ (ผลลบ)

ตั้งใจจะแทรกคำใบ้หลัง `Wait` และ `Alternatively` ตาม START (H5) แต่บนแขนนี้

| คำ | ต่อ 1,000 token | หน้าต่างที่มีคำนี้ โปรแกรมตอบได้ | หน้าต่างที่ไม่มี |
|---|---:|---:|---:|
| `Wait` | 0.04 | 53 % | 46 % |
| `Alternatively` | 0.01 | 0 จาก 2 | 46 % |
| `Let's test` และคำคล้ายกัน | 0.80 | 49 % | 44 % |
| `But` | 2.15 | 43 % | 55 % |

โมเดลนี้แทบไม่ใช้สองคำของ START และทุกคำแยกงานที่โปรแกรมตอบได้ออกจากงานอื่นไม่ได้ ตรงกับ [2510.20342](https://arxiv.org/abs/2510.20342) ที่ว่าการวางคำใบ้อัตโนมัติยังไม่แม่นพอ **H5 จึงยกเลิก**

### ข้อง่าย: token อยู่หลังคำตอบ

เป้าหมายของข้อที่โมเดลทำได้อยู่แล้วคือลด token จึงวัดว่าการคิดหลังคำตอบปรากฏครั้งแรกมีเท่าไร แขนไม่มี MIP บนข้อที่ตอบถูก

| | MATH 273 ข้อ | GSM8K 175 ข้อ |
|---|---:|---:|
| Token ของการคิด | 206,345 | 65,503 |
| หลังคำตอบปรากฏครั้งแรก | 76 % | 64 % |
| มีคำว่า `Let's verify` และคำคล้ายกันหลังคำตอบ | 114 ข้อ | 14 ข้อ |
| หลังคำนั้น | 54 % | 9 % |

เลขแถวที่ 2 เป็นเพดานบน เพราะเลขตัวเดียวกันอาจโผล่ก่อนโดยบังเอิญ คำเหล่านี้ใช้หางานของโปรแกรมทั่วไปไม่ได้ แต่เป็นจุดที่โมเดลตัดสินใจจะตรวจด้วยมือเอง ซึ่งแม่นกว่าการเดา **`--igc-sandbox-verify` จึงต่อประโยคนั้นให้เป็นการตรวจด้วยโปรแกรม** ไม่เกิน 3 ครั้งต่อการคิด ผลบน MATH น่าจะชัดกว่า GSM8K

### กฎที่ด่านก่อนจบ (แขน `lg`)

2 ข้อ แล้วหยุดเพราะได้คำตอบแล้ว

| ข้อ | ผล | Token | สิ่งที่เกิด |
|---|---|---|---|
| 3364 | **ถูก** | 12,782 | เขียน stub, ผล `None`, เขียนโค้ดจริง, ตัวอย่างผ่าน 3 ข้อ แล้ววนเขียน test เดิม 8 รอบ |
| 3478 | ผิด | 46,947 | ก๊อปคำใบ้เป็น comment ใน block ว่าง 8 รอบ ทั้งที่เขียนร่างไว้แล้ว 4 ร่าง |

ทั้งสองปัญหามาจากกฎของเรา ไม่ใช่จากโมเดล

## งานวิจัยที่เปลี่ยนกฎ

งานวิจัยรวบรวมจากการอ่านผ่านเครื่องมือดึงหน้าเว็บ ตัวเลขใช้เป็นแนวทาง ไม่ใช่ข้อพิสูจน์บนโมเดลเรา

| ผลการศึกษา | ที่มา | กฎที่เปลี่ยน |
|---|---|---|
| ร่างผิดในบริบททำให้คะแนนตกแรง GPT-OSS-20B AIME24 51.88 → 17.50 แม้บอกว่าผิดก็ไม่กลับมา | [2602.04288](https://arxiv.org/abs/2602.04288) | ผลไม่ตรงต้องนำไปสู่การรันใหม่ทันที อ่านอย่างเดียวไม่พอ |
| ที่จุดปิดการคิด คำว่า `let` เพิ่มคะแนน คำว่า `wait` ลด | [2606.16934](https://arxiv.org/abs/2606.16934) | เปลี่ยนคำที่ด่านแล้ว |
| การประกาศ tool ใน prompt ใช้ไม่ได้บน R1 และ QwQ-32B | [2504.16891](https://arxiv.org/abs/2504.16891) | ตรงกับที่เราวัดได้ 0 block จาก 88 run |
| การตรวจซ้ำกิน 16.8-47.8 % ของ token แต่แก้จากผิดเป็นถูกไม่ถึง 2 % | [2510.08308](https://arxiv.org/abs/2510.08308) | ปิดเมื่อ test ผ่านน่าจะคุ้ม ต้องวัดข้อที่ถูกด้วย |
| งาน early stop ทุกชิ้นเสียคะแนน 0.9-5.2 จุด | [2604.06787](https://arxiv.org/abs/2604.06787) [2510.08308](https://arxiv.org/abs/2510.08308) [2604.04930](https://arxiv.org/abs/2604.04930) | ปิดได้เฉพาะเมื่อมีผล test เป็นหลักฐาน |
| LiveCodeBench หลาย attempt แล้วคัดด้วย test ชนะการแก้ต่อเนื่อง Gemini Flash 62.2 → 77.84 ที่ N=8 เป็นเพดาน | [2604.05868](https://arxiv.org/abs/2604.05868) | ไพ่ใบใหญ่ที่สุดที่ยังไม่ได้ลอง |

| โมเดลปัดผลที่ถูกทิ้งได้ และ agent มองข้ามผลที่หามาแล้ว 68 % ของ trace | [2406.19228](https://arxiv.org/abs/2406.19228) [2604.18805](https://arxiv.org/abs/2604.18805) | ผลไม่ตรงต้องมีบรรทัดของโมเดลต่อ ซึ่งทำแล้ว |

ไม่พบงานที่ทดสอบ inline calculator บนโมเดลใหญ่ที่ไม่ได้ train ใหม่ และไม่พบงานที่ทดสอบการแตก greedy ด้วย prefix ต่างกันบนโมเดลให้เหตุผล

## กฎใหม่ (commit d77db1ed)

| เดิม | ใหม่ | เหตุผล |
|---|---|---|
| เปิด block ตามจำนวน token | รันร่างที่โมเดลเขียนเองทันทีที่ปิด fence, ทุกร่าง (`--igc-sandbox-draft`) | ร่างคือสมมติฐานที่พร้อมทดสอบ |
| ด่านขอให้เขียนโค้ดใหม่ | ด่านเรียกร่างที่นิยามไว้แล้ว | ไม่ต้องพิมพ์ซ้ำ และไม่มี block ว่าง |
| ตัวอย่างผ่านแล้วคิดต่อ | ผ่านที่ด่านแล้วจบทันที | โมเดลตัดสินใจจบอยู่แล้ว จึงไม่ได้ตัดอะไร |
| `expect` รับ 2 ค่า | รับ `expect(f(x) == 3)` ด้วย | เป็นรูปที่โมเดลเขียนเองครั้งแรก |
| บรรทัดเปิดเป็นคำใบ้ของ START | `Let me run my code on the examples before I answer.` | คำใบ้เดิมถูกก๊อปเป็น comment |

ส่วน `--igc-sandbox-pass-close` (จบเมื่อ test ผ่านที่จุดใดก็ได้) และ `--igc-sandbox-falsify` (ถามต่อว่า input ใดจะทำให้พัง) เป็นแขนทดลอง ปิดอยู่โดยปริยาย

**`--igc-sandbox-brute`** มาจากผลของ API block ที่เปิดหลัง token N เปลี่ยนจากคำสั่งกว้างๆ เป็นการขอ `def brute(` จากโจทย์ แล้วรันกับตัวอย่าง เหตุผล 3 ข้อ

1. แก้ปัญหาเข้าใจโจทย์ผิดได้ตั้งแต่ต้น แบบข้อ 3608
2. เมื่อมี oracle แล้ว ทุกสมมติฐานถัดไปทดสอบได้ ไม่ต้องไล่ด้วยมือ
3. ร่างที่ผ่านตัวอย่างจะถูกเทียบกับ brute force บน input สุ่ม (ร่วมกับ `--igc-sandbox-falsify`) ซึ่งแรงกว่าตัวอย่างในโจทย์

Oracle ที่เขียนจากโจทย์เป็นอิสระจากวิธีเร็วของโมเดล จึงมีจุดบอดร่วมกันน้อยกว่า test ที่เขียนจากโค้ดตัวเอง ([PGS](https://arxiv.org/abs/2506.18315) ชี้เรื่องจุดบอดนี้) ส่วน pass ที่ brute force เองไม่นับเป็นหลักฐานของคำตอบ

## สิ่งที่ยังไม่รู้
