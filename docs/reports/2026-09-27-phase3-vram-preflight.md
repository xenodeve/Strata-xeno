# Phase 3 display GPU VRAM preflight

Scope: Strata-xeno #3 / Flash-Next tracker #12. This is a read-only safety and device-identity probe, **not** static expert placement.

The developer set a minimum of 2.5 GB free on the display RTX 4070 SUPER. The code uses 2560 MiB (2.5 GiB) as a conservative floor. `CUDA_VISIBLE_DEVICES=1,0` must map the 5060 Ti to CUDA device 0 and the 4070 SUPER to CUDA device 1. `strata-device --device 1 --secondary-reserve-mib 2560` checks both identities and the second device's `sm_89` capability. The NVML query locates that exact card using its PCI bus ID, rather than assuming NVML index 1 is CUDA index 1.

The budget helper sizes 256-byte aligned profile slots in ranking order and stops at the first one that does not fit. Its CTest went red before implementation because the header was absent; after implementation it passed reserve, alignment, profile truncation, overflow and lower-of-two-readings cases. The CLI initially rejected `--device`; after implementation the dual-arch build and real device probe passed. It also rejects a 2559 MiB reserve, missing reserve and wrong device order. No model was run on the 4070 SUPER, and this check makes no GPU allocation.

Three repeated probes of the same device showed CUDA free 10.810 GiB while `nvidia-smi` showed about 9810–9812 MiB. A later probe reported CUDA 10.810 GiB, NVML 9.800 GiB; the planner therefore used 9.800 GiB and reported at most 7.300 GiB before touching an allocation. Readings vary with desktop activity, and the NVML figure differed slightly between in-process query and adjacent `nvidia-smi`. The cause of the gap was not proven. NVIDIA documents that [`cuMemGetInfo` is an OS estimate and not a guarantee that all reported free bytes can be allocated](https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/group__CUDA__MEM.html), while [WDDM manages device memory](https://docs.nvidia.com/deploy/nvml-api/api/group__nvmlDeviceQueries.html). The lower figure is a conservative planning input, **not** proof that an eventual allocation leaves the reserve. The next gate must allocate, physically touch, synchronize and query again.
