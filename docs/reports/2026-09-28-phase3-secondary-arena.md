# Phase 3 secondary arena checkpoint

Scope: engine #3 / tracker #12, branch `xeno/afk-phase3`. This checkpoint allocates **only a bounded test arena** on the display GPU. Expert residency and cross-device computation are still open.

`SecondaryArena` takes profile-ranked blob byte sizes and an explicit byte cap, aligns slots to 256 bytes and allocates on CUDA device 1 only after checking that visible device 0 is the 5060 Ti and device 1 is the 4070 SUPER (`sm_89`). Its free-memory snapshot uses the lower of CUDA and PCI-matched NVML readings. It plans with an extra 64 MiB allocation cushion above the hard 2560 MiB free floor, touches and synchronizes the whole allocation, then re-queries both readings. If the floor is breached, it releases its own allocation and retries with fewer whole ranked slots, up to eight attempts. NVML/CUDA query failures and non-memory CUDA failures stop the attempt. The arena owns only its allocation and restores the prior CUDA device after open/close.

The CPU budget test went red before `max_bytes` and retry-prefix logic existed, then passed. The hardware smoke test went red before the arena header existed, then built. With `CUDA_VISIBLE_DEVICES=1,0`, it allocated and touched 64 one-MiB slots, checked the last byte was zero, confirmed the sampled lower free memory stayed above 2560 MiB and released the allocation. `nvidia-smi` before and after the hardware test both showed 1,862 MiB used / 10,136 MiB free on the 4070 SUPER in one run, and a later run ended with 1,906 MiB used / 10,092 MiB free as the desktop changed. The test does not load model weights or validate expert output.

The post-touch breach/retry path was then forced with injected free-memory readings during a bounded hardware test: an initial 128 MiB allocation was reported one byte below the reserve, released, and retried with 63 one-MiB slots; four readings were consumed and the second attempt succeeded. Adjacent `nvidia-smi` values were 1,962 MiB used / 10,036 MiB free before and 1,961 MiB used / 10,037 MiB free after. This tests release and whole-slot shrink without deliberately exhausting real display VRAM. `SecondaryArena` has not been connected to profile loading or verify-window dispatch. A 64 MiB test is not a safe-fit claim for a multi-GiB arena. Before making the tier active, test breach cleanup with injected readings, verify one filled expert blob from device 1, and compare its computed partial bit for bit against the accepted CPU/GPU baseline. Monitor the reserve during real requests because desktop allocations can change after startup.

## Review correction

Independent standards and spec reviews both found that the first `close()` cleared its sole device pointer even if `cudaSetDevice` or `cudaFree` failed. That would make a later release impossible. `close()` now returns success/failure and retains ownership until `cudaFree` succeeds. Early-release paths during a failed `open()` also retain an unreleased pointer with zero usable slots. Callers can retry `close()`; if destruction still cannot release display VRAM, the owning Strata process logs and terminates so it does not keep running with an untracked allocation. The normal 64 MiB allocation/release and injected 128→63 MiB breach/retry tests passed after the correction. A real driver failure could not safely be induced on the display GPU, so that rare path remains code-reviewed rather than hardware-fault tested.
